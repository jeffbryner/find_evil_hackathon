# Mission: OS Fingerprinting via TTL / TCP Stack — UA-Independent Environment Separation
**Target Agent:** sniper-forensics

## Purpose
Every conclusion in this case currently depends on **User-Agent strings**, which are application-controlled text and therefore weak evidence. Mission 012's verdict — that the Windows XP VM was shared between `jcoachj@gmail.com` and `amy789smith` — rests entirely on classifying one UA (`Mozilla/4.0 (compatible; MSIE 5.5)`) as "Windows-only." The case lead has rejected that inference: a bare `MSIE 5.5` carrying **no platform token at all** is the hallmark of a hardcoded application UA, and this laptop was demonstrably running **`Adium/1.2.7 (Mac OS X)`**, a Mac IM client that speaks the Yahoo protocol and uploads to `filetransfer.msg.yahoo.com`.

Your mission is to replace that guesswork with **network-stack fingerprinting**, which the user cannot trivially forge.

**The physics we exploit:** the Mac host OS and the VMware Windows XP guest share one IP (192.168.15.4) and one MAC, but their packets are generated by *two different TCP/IP stacks*, and the guest's packets are additionally **routed** by VMware NAT:
- **Mac OS X (host, native):** initial TTL **64** → observed on the wire as **64**. TCP timestamps ON, window scaling present, MSS typically 1460.
- **Windows XP (guest, behind VMware NAT):** initial TTL **128**, decremented once by the NAT router → observed on the wire as **127**. TCP timestamps typically OFF, distinctive initial window size (e.g. 64240/65535), different option ordering.

A clean bimodal TTL split (64 vs 127/128) is objective proof of two stacks, and lets you label **every packet** — including non-HTTP protocols — by environment.

**Answer the question the evidence supports. If the Yahoo transfer turns out to be Mac-side, say so; if it is VM-side, say so.**

## Results & Post-Mortem
- **Approach:** Ran tshark against `/case/images/nitroba.pcap` in the SIFT/NITROBA container. Extracted TTL histogram for all outbound packets from 192.168.15.4, classified all 6 anchor frames by TTL, queried TCP SYN options for the 6 anchor streams, and cross-referenced User-Agent against TTL for all HTTP from 192.168.15.4.

- **Findings:**

  **TTL METHOD: INVALID / UNRELIABLE**
  - TTL histogram: 33,392 packets at TTL 63 (dominant), 1,161 at TTL 64, 1 at TTL 126. No bimodal 64/127 split exists.
  - Root cause: VMware NAT on the host Mac resets outbound TTL to the Mac's default (64). After one routing hop through Kenny's Wi-Fi router (192.168.15.1), ALL outbound traffic arrives at the capture point with TTL 63, regardless of whether it originated from Mac OS X or the Windows XP VM.
  - Control validation FAILS: Mac controls frame 32229 (Facebook/Firefox) and frame 22757 (Computrace) both show TTL 63 — identical to VM frames 80614/83601/77508 (IE6). The method cannot separate the stacks. **Per the mission rules, the TTL method must be reported as unreliable.**
  - UA vs TTL: Every single User-Agent (Mac Safari, Mac Firefox, MSIE 6.0, iTunes, MSIE 5.5, Adium, Windows-Update-Agent) appears at TTL 63. No UA is distinguished by TTL.

  **ANCHOR FRAME TTL TABLE (all TTL 63 — method fails):**
  | Frame | Time UTC | Expected Stack | TTL | User-Agent |
  |---|---|---|---|---|
  | 22757 | 04:36:48 | Mac (control) | **63** | Safari/Mac (Computrace) |
  | 32229 | 04:50:30 | Mac (control) | **63** | Firefox/2.0.0.16 Mac |
  | 77508 | 06:00:44 | VM | **63** | MSIE 6.0/WinNT5.1 |
  | 80614 | 06:02:57 | VM | **63** | MSIE 6.0/WinNT5.1 |
  | 83601 | 06:04:24 | VM | **63** | MSIE 6.0/WinNT5.1 |
  | 90504 | 06:09:59 | DISPUTED | **63** | MSIE 5.5 |

  **TCP SYN WINDOW SIZE: VALID ALTERNATIVE FINGERPRINT**
  - The SYN initial window size cleanly separates the two stacks (TTL does not):
  | Stream | Anchor Frame | TTL | SYN Window | Classification |
  |---|---|---|---|---|
  | 468 | 22757 (Computrace/Mac control) | 63 | **65535** | Mac OS X native ✓ |
  | 624 | 32229 (Facebook/Mac control) | 63 | **65535** | Mac OS X native ✓ |
  | 1601 | 77508 (Google/jcoachj VM) | 63 | **64240** | Windows XP VM ✓ |
  | 1631 | 80614 (Hostile POST 1) | 63 | **64240** | Windows XP VM ✓ |
  | 1701 | 83601 (Hostile POST 2) | 63 | **64240** | Windows XP VM ✓ |
  | 1865 | 90504 (Yahoo/amy789smith) | 63 | **65535** | **Mac OS X native** |

  - Mac controls (streams 468, 624) validate at SYN window=65535; VM frames (streams 1601, 1631, 1701) validate at 64240. Method is sound.

  **VERDICTS:**
  (a) **Two distinct OS stacks ARE provable** — but via TCP SYN initial window size (65535=Mac, 64240=Windows XP VM), NOT via TTL. TTL is useless here.
  (b) **Hostile emails (frames 80614, 83601) came from the Windows XP VM** — streams 1631/1701 both show SYN window=64240.
  (c) **The `amy789smith` Yahoo transfer (frame 90504, stream 1865) came from the Mac OS X native stack** — SYN window=65535, matching the Mac controls. M010/M012's classification of this as "Windows XP IE 5.5 (VMware VM)" is REFUTED by TCP stack evidence.
  (d) **`Mozilla/4.0 (compatible; MSIE 5.5)` groups with the Mac stack** — it appears only in stream 1865 which has a Mac-native SYN signature. The UA is a hardcoded application string (consistent with Adium or another Mac Yahoo client), not a genuine IE browser on Windows.

- **Confidence Rating:** High (90%+) for (b) and (c) — the bimodal SYN window split cleanly aligns with the two independent Mac controls. The sole caveat: VMware NAT behavior is implementation-dependent; if NAT is application-layer proxying, the SYN characteristics would reflect the Mac stack regardless. However, the clear 65535/64240 bimodal split (not 65535/65535) strongly argues the TCP payload is preserved from the originating stack, and both controls confirm the 65535 grouping.

- **Budget Tally:** Tool calls 1-4 (Orientation), calls 5-10 (Execution: docker ps + 4 tshark batch commands + 1 SYN analysis command). Reporting: calls 11-14 (this card update, shared_facts update, audit write).

- **NPS / Feedback:** 9/10. The mission premise was correct that TTL fingerprinting is the right *theory*, but VMware NAT on the Mac resets TTL, breaking that specific method for this evidence. The fallback to TCP SYN window size delivered an equally strong (arguably stronger) fingerprint that cleanly resolves the dispute. Mission design was well-structured — the control validation requirement was exactly right, and correctly forced reporting the TTL failure rather than forcing a bad conclusion.
